Deliver all V1 audio assets and the dynamic soundscape system: adaptive music with beat-boundary crossfades, ambient beds, zone loops, vehicle engine audio, stingers, all WAV SFX assets, UI sounds, and music ducking — all wired to simulation and UI events. - [ ] Font asset: create `assets/fonts/hud_font.xml` AND `assets/fonts/hud_mono_font.xml` — **two-font path selected** (Path 2 per `architecture/ui-ux/hud-layout.md` Monospace Requirement). Decision: `hud_font.xml` is a proportional sans-serif face for labels and button text; `hud_mono_font.xml` is a monospace face applied selectively to numeric `IGUIStaticText` elements (treasury balance, population count, tax rates, percentages) via `IUIBackend::setElementMonoFont(handle)` (method 19 — see `architecture/ui-ux/ui-manager.md` §IUIBackend Method Contract) called immediately after each `addStaticText()` call. Rationale: a single monospace face applied to all HUD text (labels, tooltips, panel titles) degrades legibility at small sizes because monospace glyphs are wider than proportional equivalents, reducing the effective character capacity of compact panels such as the Query/Inspector Panel and the Tax Rate Panel. Separating the faces allows each to be optimised for its role. Both files must be bitmap fonts in Irrlicht's XML font format generated by Irrlicht's `makeFont` tool or equivalent. Both must render at minimum 11 physical pixels at 1280×720 (the hard floor from `architecture/ui-ux/resolution-ui-scaling.md`). A font sized at 16 virtual pixels satisfies this floor. `IrrlichtUIBackend` constructor already loads `hud_font.xml` and sets it as the environment default; the `hud_mono_font.xml` load call must be added to the constructor alongside the existing `hud_font.xml` load, storing the result in a `m_monoFont` pointer used by `setElementMonoFont()` (method 19). Both loads use graceful fallback (log a warning, do not assert) when the file is absent. **Font selection guidance for `gamedesign-ux`**: for `hud_font.xml`, a clean humanist or geometric sans-serif face (e.g. DejaVu Sans, Ubuntu, or Noto Sans) at 16 px virtual is recommended — these are freely licensed, render cleanly at small sizes, and are already common in game HUD toolchains. For `hud_mono_font.xml`, a tabular-figures monospace face (e.g. DejaVu Sans Mono, Ubuntu Mono, or Noto Sans Mono) is recommended. The two faces should share similar x-height and cap-height to avoid visual jarring when proportional and monospace text appear adjacent in the resource bar. ### Risks & Spikes

- **RISK**: Beat-boundary crossfade accuracy (±1 buffer period ≈ ±371 ms) may be audibly noticeable at slow tempos. **Spike**: test with 90 BPM stems at 1× speed; verify crossfade lands within the first beat of a bar.
- **RISK**: Interrupted crossfade `t_offset` formula uses arccos — verify no domain error when `current_gain_out` is exactly 0.0 or 1.0. **Spike**: unit test interrupted crossfade at t=0 and t=1 boundaries.
- **RISK**: `AL_BUFFERS_QUEUED` read order relative to `alSourceUnqueueBuffers` is critical — reading after unqueue produces underestimated queue depth and premature crossfade fire. **Spike**: add the `AudioStream_BarBoundary_UsesConsistentBuffersQueuedPerWake` test before any music integration to enforce ordering.
- **RISK**: Day→night direct ambient crossfade may sound unnatural — the day bed's energetic tail may clash with the night bed's quiet opening at the 3 s crossfade overlap. **Spike**: produce the `crossfade_demo_day_to_night.ogg` demo early in ambient bed production (before mastering the final 90–120 s beds) so that structural tail/head content decisions can be made while rework cost is still low. If the overlap sounds harsh, adjust the day bed's tail energy downward in the final 10 s and/or adjust the night bed's head to have a gentle upward entry rather than an immediate full-level start.
- **RISK (fallback path resolved)**: `nvcompress` RGBA byte-order guarantee vs. platform-specific build variation — the `-rgba -nomips` flags are documented for NVTT 2.x. Verify the installed nvcompress version and its RGBA byte order output before committing the sprite sheet. **Spike**: create a 2×2 red pixel test PNG (`R=255, G=0, B=0, A=255`), convert with `nvcompress -rgba -nomips red_test.png red_test.dds`, then decode the DDS and inspect the first pixel value — it must read R=255, G=0, B=0 in the output PNG; a B=255 result indicates BGRA byte-order and the nvcompress version must not be used for this asset. **Resolved fallback**: if the byte-order check fails, skip the nvcompress DDS intermediate entirely and export `hud_sprites_ui.png` directly from the DCC tool as a lossless 32-bit RGBA PNG. The PNG is pixel-identical to a correct RGBA8 UNORM DDS for uncompressed data and Irrlicht loads it correctly via `getTexture()`. The DDS intermediate step exists only to validate RGBA byte order; when the validation fails, the PNG export from the DCC tool is the approved alternative. This resolution is documented in the Sprite Sheet deliverable authoring pipeline step 3 above.
- **RISK**: `hud_mono_font.xml` and `hud_font.xml` may have mismatched x-heights, causing visual jarring in the resource bar where proportional label text and monospace numeric text appear on the same row. **Spike**: render a sample resource bar string such as "Treasury: $123,456" using both fonts side-by-side in a test render; if cap-height differs by more than 2 physical pixels at 1280×720, select fonts from the same type family (e.g. Noto Sans + Noto Sans Mono) which share x-height by design.
- **RISK (decided 2026-03-04 — no per-tick cap in V1)**: `sfx_intersection_tick` fires on every signal phase change across the entire map; at high city scales (hundreds of intersections) this could generate hundreds of `playPositionalSound` calls per simulation tick, causing SFX pool churn. **Decision**: no per-simulation-tick cap is added in V1. The 80 m pre-acquisition distance cull (enforced in `CitySimulation::tick()` via `m_renderer->getListenerPosition()`) is the primary throttle — it eliminates all calls beyond audible range. The `SoundPriority::LOW` eviction policy ensures the pool self-manages under contention: excess intersection calls are silently dropped rather than evicting higher-priority SFX. If integration testing reveals unacceptable pool churn at maximum city scale, add a per-tick cap of 8 `sfx_intersection_tick` acquisitions (closest-to-listener first) as a Phase 10 patch — but do not add it pre-emptively before profiling evidence.
- **RISK (decided 2026-03-04 — per-wave-tick call cap of 3)**: `sfx_zone_upgrade` fires once per upgraded tile during a density upgrade wave; a wave upgrading many tiles could produce a jarring burst of simultaneous sounds. **Decision**: add a per-wave-tick call cap of **3** in `CitySimulation::doDensityUnlockTick()`. After 3 `m_audio->playSound(SFX_ZONE_UPGRADE, ...)` calls in a single invocation of `doDensityUnlockTick()`, subsequent tile upgrades in the same tick are completed silently (the tile is still upgraded — only the audio call is suppressed). The cap is enforced by a local `int sfxCallsThisTick = 0` counter in `doDensityUnlockTick()`: increment on each audio call; skip audio when `sfxCallsThisTick >= 3`. Rationale: 3 simultaneous plays is enough to communicate "upgrade wave happening" to the player; at most 3 NORMAL-priority pool slots are consumed per wave tick; the full burst variant (one call per tile) risks pool exhaustion and mix incoherence. The 3-call cap is a `SimulationConstants::sfx_zone_upgrade_per_tick_cap = 3` named constant in `simulation_constants.h` — do not hardcode the literal `3` in `doDensityUnlockTick()`.
- **RISK (decided 2026-03-04 — Phase 11 tracking item confirmed)**: `tile.alertFired`, `tile.wasPowered`, and `tile.wasWaterCovered` are per-tile bools that must be serialised in the save file. The save system spec (`architecture/game-design/service-coverage.md` "Per-Tile Audio Transition Fields" section) already documents this requirement including the default-initialization rule for saves written before Phase 10. Phase 10 does not implement serialisation (that is Phase 11 scope). The known gap — service alert SFX re-fire on save/load if the save was written during Phase 10 before Phase 11 ships — is accepted and tracked as a Phase 11 integration item. No additional spec work is required before Phase 10 exit.
