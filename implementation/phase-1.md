## Phase 1: Irrlicht Device Shell & Camera

### Goal

Establish the Irrlicht device lifecycle, render loop call order, `CameraController`, `IRenderer` interface, and `IrrlichtUIBackend` compile target — giving all subsequent phases a working, compilation-verified display target to build against, before any GL capability queries or texture infrastructure is added in Phase 2.

- [x] **`glewInit()` in `RenderSystem` constructor** (`graphics-dev-irrlicht`): immediately after `createDevice()` returns non-null (guard the `EDT_NULL` short-circuit path), the `RenderSystem` constructor MUST:
  1. Set `glewExperimental = GL_TRUE` then call `glewInit()`.
  2. Handle `GLEW_ERROR_NO_GL_VERSION` as a non-fatal warning (log and continue — do NOT abort, do NOT fall back to `EDT_NULL`).
  3. **Three-tier response based on `glewResult`**:
     - **SUCCESS path** (`glewResult == GLEW_OK` OR `glewResult == GLEW_ERROR_NO_GL_VERSION`): call `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &m_maxTextureSize)`; store result as member `m_maxTextureSize`. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md` step 3)
     - **Fatal failure in DEBUG builds** (any other `glewResult`): abort immediately (hard assert or `std::abort()`).
     - **Fatal failure in RELEASE builds** (any other `glewResult`): call `m_device->drop(); m_device = nullptr;` BEFORE calling `irr::createDevice(EDT_NULL, ...)`, then assign the new device. **ISSUE-P — GL defaults MUST be set immediately after `EDT_NULL` creation, before any subsequent code that might read these members**: After the new `EDT_NULL` device is assigned, the constructor MUST set ALL THREE GL-dependent member defaults WITHOUT calling any GL functions: `m_maxTextureSize = 2048; m_srgbTextureSupported = false; m_maxAnisotropy = 1.0f;`. These three assignments MUST occur after `EDT_NULL` device creation and MUST appear before the `glewInit()` SUCCESS-path query block — the SUCCESS-path block is skipped entirely in the RELEASE fallback (there is no GL context to query). The order is: (1) drop old device; (2) create `EDT_NULL` device; (3) set the three GL defaults WITHOUT any GL call; (4) display user-facing error notification; (5) return from constructor or skip the remainder. The three defaults MUST NOT be deferred to member initialization in the class definition — they must be explicitly set in this RELEASE fallback code path so that code inspection can verify the fallback path without ambiguity about whether defaults were set by the constructor body or the member initializer list. Display a user-facing error notification. NOTE: Dropping the old device BEFORE creating the `EDT_NULL` replacement is mandatory — the old OpenGL device holds GL state that conflicts with any subsequent GL calls; dropping it first ensures a clean handoff. This order (drop old → create EDT_NULL → set defaults → notify) is a named exit criterion checklist item and must be verified by code inspection before Phase 1 PR merges.

  The `glewInit()` call MUST be placed AFTER the device-type check: if the device is `EDT_NULL` (headless CI), glewInit() MUST NOT be called at all — there is no OpenGL context to initialize GLEW against. Only call `glewInit()` when `device->getVideoDriver()->getDriverType() != EDT_NULL`.

  This requires `find_package(GLEW REQUIRED)` and linking `GLEW::GLEW` BEFORE `Irrlicht` in `aitown_render` (see co-landing requirement in Windows DLL CI section below). The Phase 2 GLEW spike answers whether the vendored Irrlicht build strips its bundled GLEW — the `glewInit()` call itself is a **Phase 1 mandatory requirement**, not a Phase 2 deliverable.

  **Cross-reference note on `glewInit()` tier structure**: The plan describes a "three-tier response based on `glewResult`" (SUCCESS / DEBUG fatal / RELEASE fatal). This maps to the spec's two-path structure in `architecture/graphics-architecture/irrlicht-device-lifecycle.md` as follows: the spec defines (1) SUCCESS path (`GLEW_OK` or `GLEW_ERROR_NO_GL_VERSION`) and (2) FAILURE path (any other result, with debug/release sub-behaviours). **`EDT_NULL` is an OUTER guard that short-circuits the entire GL capability block BEFORE `glewInit()` is called — it fires first, before any `glewResult` check.** It is NOT a third tier within the `glewResult` switch. The plan's "three-tier response" refers exclusively to the three code-path outcomes from the `glewResult` switch (SUCCESS, DEBUG-abort, RELEASE-fallback), which are only reached AFTER the `EDT_NULL` outer guard has already passed. In code-flow order: (1) check device type — if `EDT_NULL`, skip `glewInit()` entirely and set defaults; (2) only if NOT `EDT_NULL`, call `glewInit()` and evaluate `glewResult` against the three tiers (SUCCESS / DEBUG-fatal / RELEASE-fatal). Both the plan and the spec are consistent under this reading. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`)
