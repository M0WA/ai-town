## Phase 1: Irrlicht Device Shell & Camera

### Goal

Establish the Irrlicht device lifecycle, render loop call order, `CameraController`, `IRenderer` interface, and `IrrlichtUIBackend` compile target — giving all subsequent phases a working, compilation-verified display target to build against, before any GL capability queries or texture infrastructure is added in Phase 2.

### Deliverables

#### Graphics / Render System

- [ ] `RenderSystem` class: owns `IrrlichtDevice*` (RAII, `device->drop()` in destructor); `EDT_OPENGL` on all platforms; log and abort if OpenGL unavailable (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`)
- [ ] `SIrrlichtCreationParameters`: `EDT_OPENGL`, `Bits=32`, `ZBufferBits=24`, `Stencil=true`, `AntiAlias=4`, `Vsync=false`, initial window `1280×720` (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`)
- [ ] **`glewInit()` in `RenderSystem` constructor** (`graphics-dev-irrlicht`): immediately after `createDevice()` returns non-null (guard the `EDT_NULL` short-circuit path), the `RenderSystem` constructor MUST:
  1. Set `glewExperimental = GL_TRUE` then call `glewInit()`.
  2. Handle `GLEW_ERROR_NO_GL_VERSION` as a non-fatal warning (log and continue — do NOT abort, do NOT fall back to `EDT_NULL`).
  3. **Three-tier response based on `glewResult`**:
     - **SUCCESS path** (`glewResult == GLEW_OK` OR `glewResult == GLEW_ERROR_NO_GL_VERSION`): call `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &m_maxTextureSize)`; store result as member `m_maxTextureSize`. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md` step 3)
     - **Fatal failure in DEBUG builds** (any other `glewResult`): abort immediately (hard assert or `std::abort()`).
     - **Fatal failure in RELEASE builds** (any other `glewResult`): re-initialize the device with `EDT_NULL`; set `m_maxTextureSize = 2048` WITHOUT calling `glGetIntegerv` (no GL context is current after `EDT_NULL` re-init); display a user-facing error notification.

  This requires `find_package(GLEW REQUIRED)` and linking `GLEW::GLEW` BEFORE `Irrlicht` in `aitown_render` (see co-landing requirement in Windows DLL CI section below). The Phase 2 GLEW spike answers whether the vendored Irrlicht build strips its bundled GLEW — the `glewInit()` call itself is a **Phase 1 mandatory requirement**, not a Phase 2 deliverable.

  2. `// TODO Phase 6: citySimulation.tick(realDeltaSeconds)` — stub comment at main loop call site; do NOT implement until Phase 6; `WallClock::nowSeconds()` delta must be computed here as raw real-world frame delta (NEVER pre-multiplied by speed multiplier — `CitySimulation` owns all speed-scaling internally per `architecture/game-design/simulation-time.md`). **`CitySimulation` must be constructed with default speed `SpeedMultiplier::x3` per `architecture/game-design/simulation-time.md` — NOT `x1` or `Paused`.   3b. `UIManager::update(realDeltaSeconds)` — per-frame UI state update (undo countdown, grace-period indicator, notification auto-dismiss timers).   4b. `AudioSystem::update(realDeltaSeconds)` — then performs ALL three main-thread responsibilities: (1) advance occlusion raycast budget and process per-source distance cull checks (depends on listener position committed by step 4a); (2) push time-of-day transitions; (3) QUEUES crossfade command objects to the audio thread via a mutex-protected command queue; `AudioSystem::update()` MUST NOT call `alSourcef(AL_GAIN)` directly on streaming sources from the main thread (per `architecture/audio-architecture/dynamic-soundscape.md`).   5. `RenderSystem::beginFrame()` — wraps `driver->beginScene()`
  6. `RenderSystem::drawScene()` — wraps `sceneManager->drawAll()` + `uiManager->draw()` (both inside the single `beginScene`/`endScene` pair)
  7. `RenderSystem::endFrame()` — wraps `driver->endScene()`

  **realDeltaSeconds provenance**: `realDeltaSeconds` (or `dt`) is the raw `WallClock::nowSeconds()` delta computed ONCE per frame at the top of the frame loop before step 3. The same raw wall-clock delta is passed to both `CameraController::update(dt)` (step 3) and `AudioSystem::update(realDeltaSeconds)` (step 4b) — no speed multiplier is applied at any intermediate step between these calls. The variable must be computed as `realDeltaSeconds = currentTime - previousTime` at the top of the frame before step 3.

  **OAL-2 ordering rule**: `CameraController::update(dt)` at step 3 MUST execute BEFORE `AudioSystem::syncListenerToCamera(cameraState)` at step 4a — the listener must read the camera position AFTER it has been updated for the current frame. **Step 4a MUST precede step 4b** — `update()` advances the occlusion raycast budget using per-source distance cull checks that reference the current listener position already committed to the OpenAL context by `syncListenerToCamera()`; processing occlusion checks before the listener is updated would use one-frame-stale position data. Additionally, `update()` pushes pending time-of-day transitions and zone-layer source cull/acquire decisions (per `IAudioSystem::update()` docstring in `architecture/audio-architecture/audio-system.md`); these writes must complete before `beginScene()` to avoid interleaving state mutations inside the Irrlicht begin/end scene block. (Note: gain writes to streaming sources are the audio thread's exclusive responsibility — not performed by main-thread `update()`.) The OAL-2 rule comment at the main loop call site must document ALL three main-thread responsibilities of `AudioSystem::update()`: (1) occlusion raycast budget + distance cull checks, (2) time-of-day transition pushing, (3) pending crossfade/zone-layer source update forwarding. **A comment covering only responsibility (1) does NOT satisfy the Phase 1 exit criterion for this comment.** This sequence must be documented as a comment at the main loop call site. **OAL-2 mutex contract for GAINHF transitions**: Per-source occlusion GAINHF state-change writes (`m_fnFilterf`/`alSourcei` calls for the GAINHF transition) made from the main thread during the raycast pass MUST hold `m_occlusionMutex`. Only `m_occlusionGainTarget[i].store()` is safe without the mutex (it is `std::atomic<float>`). See `architecture/audio-architecture/audio-occlusion.md` for the full thread-safety contract. The OAL-2 comment at the main loop call site MUST document this threading constraint as part of responsibility (1)'s description. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`, `architecture/audio-architecture/audio-system.md`, `architecture/audio-architecture/spatial-audio.md`, `architecture/audio-architecture/audio-occlusion.md`, `architecture/ui-ux/ui-manager.md`)

- [ ] Platform `IEventReceiver` adapter in `src/platform/` that translates Irrlicht `SEvent` to `InputEvent` — populates `x/y` via `UIScaler::unproject()` and `physX/physY` from raw `SEvent` mouse coordinates; forwards to `UIManager::onEvent()` then to `CameraController::OnInputEvent()` per the 6-priority input arbitration chain. **Short-circuit dispatch rule (MUST be authored in Phase 1)**: call `UIManager::onEvent(event)` first; only if it returns `false` (event not consumed) forward to `CameraController::OnInputEvent(event)`. Exception — camera pass-through events (MMB drag: `MouseButtonDown/Up button=2`, `MouseMove` while MMB held, `MouseWheel`) always reach `CameraController` regardless of `UIManager::onEvent()` return value, per `input-arbitration.md` Priority 1 pass-through rule. **RMB drag distinction**: The adapter tracks `m_rmbDragActive` boolean state: set to `true` on `MouseButtonDown button=1`; cleared on `MouseButtonUp button=1`. `MouseMove` events while `m_rmbDragActive == true` always pass through to `CameraController` regardless of `UIManager::onEvent()` return value. The `MouseButtonDown button=1` event itself is forwarded to `UIManager::onEvent()` first; if `UIManager` returns `true` (scrim consumed the click), `m_rmbDragActive` is NOT set and the event does not reach `CameraController`. If `UIManager` returns `false`, `m_rmbDragActive` is set and the drag sequence begins. This matches the intent of `architecture/ui-ux/input-arbitration.md` — RMB drag (rotate/pan) bypasses the scrim while bare RMB clicks can be consumed by an active modal. Window focus events (`WindowFocusGained`, `WindowFocusLost`) also always reach `CameraController` regardless of `UIManager::onEvent()` return value — `CameraController` is the sole consumer of these events for `m_appHasFocus` state management. This dispatch contract must be authored in Phase 1 even though UIManager is a stub — Phase 3 integration must not require structural rework of the adapter. **MMB drag tracking (`m_mmbDragActive`)**: The adapter must also track `m_mmbDragActive` (bool, initialized to `false`), set to `true` on `MouseButtonDown button=2`, cleared on `MouseButtonUp button=2`. `MouseMove` events while `m_mmbDragActive == true` always pass through to `CameraController` regardless of `UIManager::onEvent()` return value — identical in structure to the `m_rmbDragActive` tracking for RMB. The three unconditional pass-through categories must each be handled distinctly: (1) scroll-wheel — direct bypass, no state tracking needed; (2) MMB drag — `m_mmbDragActive` state tracking; (3) RMB drag — `m_rmbDragActive` state tracking. **Explicit initialization requirement**: `m_rmbDragActive` and `m_mmbDragActive` MUST be initialized to `false` in the adapter constructor. Recommended form: declare as `bool m_rmbDragActive{false};` and `bool m_mmbDragActive{false};` in the class definition. Any non-initialized bool member has indeterminate value in C++ — a misfire before the first button click would bypass `UIManager::onEvent()` for all MouseMove events. **Scrim LMB/RMB comment block (MUST be present)**: The dispatch contract MUST also document — as a comment at the call site in the platform adapter — that `UIManager::onEvent()` returning `true` for a left-click (`MouseButtonDown button=0`) or right-click (`MouseButtonDown button=1`) event while a modal is active is CORRECT behavior (the scrim element is consuming those events at Priority 1 per `architecture/ui-ux/input-arbitration.md`). Phase 8 integration MUST NOT reinterpret `UIManager::onEvent()` returning `true` for those events as a bug. (ref: `architecture/ui-ux/input-arbitration.md`, `architecture/testing/testability-architecture.md`)
