## Phase 1: Irrlicht Device Shell & Camera

### Goal

Establish the Irrlicht device lifecycle, render loop call order, `CameraController`, `IRenderer` interface, and `IrrlichtUIBackend` compile target — giving all subsequent phases a working, compilation-verified display target to build against, before any GL capability queries or texture infrastructure is added in Phase 2.

- [ ] `SIrrlichtCreationParameters`: `EDT_OPENGL`, `Bits=32`, `ZBufferBits=24`, `Stencil=true`, `AntiAlias=4`, `Vsync=false`, initial window `1280×720` (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`)
- [ ] **`glewInit()` in `RenderSystem` constructor** (`graphics-dev-irrlicht`): immediately after `createDevice()` returns non-null (guard the `EDT_NULL` short-circuit path), the `RenderSystem` constructor MUST:
  1. Set `glewExperimental = GL_TRUE` then call `glewInit()`.
  2. Handle `GLEW_ERROR_NO_GL_VERSION` as a non-fatal warning (log and continue — do NOT abort, do NOT fall back to `EDT_NULL`).
  3. **Three-tier response based on `glewResult`**:
     - **SUCCESS path** (`glewResult == GLEW_OK` OR `glewResult == GLEW_ERROR_NO_GL_VERSION`): call `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &m_maxTextureSize)`; store result as member `m_maxTextureSize`. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md` step 3)
     - **Fatal failure in DEBUG builds** (any other `glewResult`): abort immediately (hard assert or `std::abort()`).
     - **Fatal failure in RELEASE builds** (any other `glewResult`): re-initialize the device with `EDT_NULL`; set `m_maxTextureSize = 2048` WITHOUT calling `glGetIntegerv` (no GL context is current after `EDT_NULL` re-init); display a user-facing error notification.

  The `glewInit()` call MUST be placed AFTER the device-type check: if the device is `EDT_NULL` (headless CI), glewInit() MUST NOT be called at all — there is no OpenGL context to initialize GLEW against. Only call `glewInit()` when `device->getVideoDriver()->getDriverType() != EDT_NULL`.

  This requires `find_package(GLEW REQUIRED)` and linking `GLEW::GLEW` BEFORE `Irrlicht` in `aitown_render` (see co-landing requirement in Windows DLL CI section below). The Phase 2 GLEW spike answers whether the vendored Irrlicht build strips its bundled GLEW — the `glewInit()` call itself is a **Phase 1 mandatory requirement**, not a Phase 2 deliverable.

  **Cross-reference note on `glewInit()` tier structure**: The plan describes a "three-tier response based on `glewResult`" (SUCCESS / DEBUG fatal / RELEASE fatal). This maps to the spec's two-path structure in `architecture/graphics-architecture/irrlicht-device-lifecycle.md` as follows: the spec defines (1) SUCCESS path (`GLEW_OK` or `GLEW_ERROR_NO_GL_VERSION`) and (2) FAILURE path (any other result, with debug/release sub-behaviours). The `EDT_NULL` pre-check is a separate outer guard that short-circuits the entire GL capability block BEFORE `glewInit()` is called — it is NOT a third tier within the `glewResult` response. The plan's "three-tier response" refers only to the three code-path outcomes from the `glewResult` switch (SUCCESS, DEBUG-abort, RELEASE-fallback); the `EDT_NULL` short-circuit is an outer guard that precedes the `glewResult` check. Both the plan and the spec are consistent under this reading. (ref: `architecture/graphics-architecture/irrlicht-device-lifecycle.md`)

  **`m_srgbTextureSupported` GL extension query (Phase 1 mandatory)**: Immediately after the `glewInit()` SUCCESS path (once `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &m_maxTextureSize)` is performed), the `RenderSystem` constructor MUST query `GL_EXT_texture_sRGB` extension support and store the result as `bool m_srgbTextureSupported`. The query is: `m_srgbTextureSupported = (glewIsExtensionSupported("GL_EXT_texture_sRGB") == GL_TRUE);`. Even though sRGB textures are not uploaded until Phase 9, this query MUST be present in Phase 1 to avoid adding a constructor side-effect mid-pipeline — a constructor that queries GL state is an observable side-effect, and introducing it in Phase 9 would violate the principle that Phase 9 does not structurally change already-tested components. The `m_srgbTextureSupported` member must be declared in `RenderSystem.h` and initialized to `false` in the RELEASE fatal-failure path (where `m_maxTextureSize` also defaults to 2048 without a GL query). In the EDT_NULL short-circuit path (headless test/CI), `m_srgbTextureSupported` must also default to `false`.

  **`m_maxAnisotropy` query (Phase 1 mandatory — same-timing as `m_maxTextureSize`)**: In the `glewInit()` SUCCESS path (alongside `glGetIntegerv(GL_MAX_TEXTURE_SIZE, &m_maxTextureSize)`), the `RenderSystem` constructor MUST also:
  - Declare `float m_maxAnisotropy` in `RenderSystem.h`, initialized to `1.0f`.
  - Check `GL_EXT_texture_filter_anisotropic` extension via `glewIsExtensionSupported("GL_EXT_texture_filter_anisotropic")`; if present, call `glGetFloatv(GL_MAX_TEXTURE_MAX_ANISOTROPY_EXT, &m_maxAnisotropy)`; if absent, log warning and leave `m_maxAnisotropy = 1.0f`.
  - In the EDT_NULL path and RELEASE fatal-failure path: initialize `m_maxAnisotropy = 1.0f` without any GL call.

  This query MUST be present at Phase 1 for the same reason as `m_srgbTextureSupported` — introducing a constructor GL query at Phase 2 would be a structural change to an already-tested component. (ref: `architecture/asset-standards/2d-texture-standards.md`)
