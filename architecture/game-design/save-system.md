# Save System

- **Auto-save triggers**: Every **120 real seconds** OR every **5 budget ticks**, whichever comes first — and when the player opens the Pause Menu (before displaying it). The time-based trigger ensures players at 1× speed do not lose more than 2 minutes of progress regardless of tick rate. Additionally, auto-save triggers **immediately when the forced loan dialog becomes active** (before the modal is shown), ensuring pre-crisis city state is always saved and "Load Last Save" in the game-over modal reflects a meaningful restore point. The forced-loan auto-save fires on the same tick that the deficit condition is detected, before `UIManager::showModal()` is called. This resets the 120-second auto-save timer. The timer then pauses for the duration of the blocking modal and resumes when the modal is dismissed. **Budget-tick wiring**: `ICitySimulation::consumeBudgetTicks()` returns and clears the count of budget ticks fired since the last call; `UIManager::update()` calls this each frame and forwards the count to `SaveSystem::onBudgetTick()` (one call per tick). `SaveSystem::update(realDeltaSeconds)` is called each frame (step 3c in the main loop, after `UIManager::update()`) to advance the 120-second timer.
- **Save slots**: 1 auto-save slot (overwritten silently) + 3 manual save slots (player-named or auto-named with timestamp)
- **Save format**: JSON for V1 (human-readable, debuggable); binary serialization is post-V1 optimization
- **Save file location**: `~/.config/aitown/saves/` on Linux; `%APPDATA%\aitown\saves\` on Windows (consistent with `keybindings.json` path convention)
- **Manual save**: The Pause Menu > Save button triggers a save to slot 1 in V1 (simple single-slot save, no slot picker dialog). The save clears the unsaved-changes indicator. Post-V1: a slot selection dialog showing 3 slots with timestamps; saving to an occupied slot shows a brief "Overwrite [slot name]? Yes / Cancel." confirmation. `UIManager` wires the `PauseMenuPanel::consumeSaveRequest()` poll to `SaveSystem::saveToSlot(1)` followed by `UIManager::setUnsavedChanges(false)`.
- **Quit to Desktop / Quit to Main Menu safety**: When either quit action is requested and `m_hasUnsavedChanges` is true, `UIManager` shows a blocking `ModalDialog::showUnsavedQuit()` modal instead of quitting immediately. The modal presents three options: **Save and Quit** (`DialogResult::Accept` — calls `SaveSystem::autoSave()` then dispatches the quit), **Quit Without Saving** (`DialogResult::Decline` — dispatches quit immediately), and **Cancel** (`DialogResult::Cancel` — returns to the game). The modal is dismissible via Escape (treated as Cancel). If no unsaved changes exist, quit proceeds immediately without showing the modal. `UIManager` tracks the pending quit action via `m_pendingQuit` (enum: `None`, `Desktop`, `ToMenu`) and dispatches in the following `update()` tick after the modal closes.
- **Load Last Save (Game Over)**: Loads the most recent save across all slots (auto-save or manual), sorted by timestamp. If no save exists, the "Load Last Save" button is grayed out with tooltip "No save file found."
- **Save in Scenario mode**: Scenario mode saves include scenario state (win condition progress, starting conditions). Scenario saves are stored in a dedicated `scenarios/` subdirectory.
- **Population milestone serialization**: The save JSON MUST include a `population_milestone_fired` boolean array of exactly 5 elements, one per threshold (1K/10K/50K/100K/500K). Each element is `true` once the corresponding milestone has fired; `false` otherwise. On load, `CitySimulation` restores these flags to prevent already-fired milestones from re-triggering. Default-constructed value (new game) is `[false, false, false, false, false]`. See `SimulationConstants::population_milestone_threshold_1..5` for threshold values. Cross-reference: `implementation/phase-6.md` (Phase 11 promises — milestone flag serialization note).
- **Speed multiplier serialization**: The save JSON MUST include a `speed_multiplier` field storing the integer representation of the `SpeedMultiplier` enum value active at save time. On load, `CitySimulation` restores this field so that the simulation resumes at the saved speed. After loading, `getSpeedMultiplier()` MUST return the value that was serialized. Default-constructed value (new game) is `SpeedMultiplier::x3` (the default starting speed per `architecture/game-design/simulation-time.md` — there is no `NORMAL` enum value). This field is verified by the `SaveSystem_RoundTrip_PreservesFullCityState` test in Phase 11.
- **Building variant counter serialization** (Phase 11 scope): The save JSON MUST include a `building_variant_counters` array of exactly 9 integers, representing `Zoning::m_buildingVariantCounters` indexed by `zone * 3 + tier` (where `zone` = 0/1/2 for Res/Com/Ind and `tier` = 0/1/2 for Low/Med/High). On load, `CitySimulation` restores these counters so that round-robin variant selection resumes the existing sequence rather than restarting from 0. Without this, the first tile placed after a load always receives variant `01`, producing visible repetition when the pre-save sequence had already advanced to `02`. Default-constructed value (new game) is `[0, 0, 0, 0, 0, 0, 0, 0, 0]`. This field is verified by the `SaveSystem_RoundTrip_PreservesFullCityState` test in Phase 11. Cross-reference: `architecture/asset-standards/3d-model-standards.md` §91 ("Counter serialisation is Phase 11 scope").
- **Tile footprint-origin serialization**: Each tile object in the `tiles` JSON array MUST include `fp_origin_x` and `fp_origin_z` integer fields. For origin tiles and 1×1 (Low-density) buildings, both are `-1`. For non-origin tiles in 2×2 (Medium) or 3×3 (High) footprints, they hold the coordinates of the footprint origin tile. **Omitting these fields causes double-building on load**: `rebuildCityFromSim()` uses `footprintOriginX == -1` as the criterion to place a building mesh; if all sub-tiles of a multi-tile building default to `-1`, a full mesh is spawned on each sub-tile, producing `N²` overlapping buildings. These fields are serialized as `"fp_origin_x"` / `"fp_origin_z"` and deserialized into `TileData::footprintOriginX` / `TileData::footprintOriginZ`. Backward-compat note: save files created before this field was added will have all tiles default to `-1` on load, which re-introduces the double-building bug for Medium and High density buildings in those saves.
- **`LoadResult` enum**: `ISaveSystem::loadMostRecentSave()` returns a `LoadResult` value indicating the outcome of a load attempt. Defined values: `LoadResult::Ok` (save loaded and deserialized successfully), `LoadResult::NoSaveFound` (no save files exist — load should not be attempted when the Load Game button is correctly gated by `setSaveAvailable()`), `LoadResult::Corrupted` (save files exist but all fail checksum or schema validation). `UIManager` acts on `LoadResult::Ok` only; all other results leave the game in the Main Menu state.
- **`loadMostRecentSave()` API**: `ISaveSystem::loadMostRecentSave()` loads the most recent valid save across all slots (auto-save and manual), sorted by timestamp, and deserializes it into the active `CitySimulation`. Returns `LoadResult::Ok` on success. Called by `UIManager` when `consumeLoadGameRequest()` returns `true`. This is the same underlying load operation used by the "Load Last Save" game-over flow.
- **IClock injection**: `SaveSystem` uses `IClock*` (injected at construction or via `UIManager`) to drive the 120-second auto-save timer (`SaveSystem::update(realDeltaSeconds)` advances this timer). Production passes `WallClock`; tests use `ManualClock`. See `architecture/testing/testability-architecture.md §IClock` for the canonical interface definition.
